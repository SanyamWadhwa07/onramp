    The problem

    Code gets written faster than anyone can read it.

    Coding agents ship whole features in an afternoon. The gap between the code you run and the code you understand has a name: comprehension debt. A README doesn't close it, and neither does a graph of every import.

    What you need

    A path, not a pile. Where to start, what to read next, and when you know enough for what you came to do.

    Explanations you can trust. AI-written docs are confidently wrong often enough that you end up re-reading the code anyway. Onramp treats every sentence about the code as a claim that has to point at the code and pass a check.

    The why, not only the what. Why the project is shaped this way, in the order it was built, from the history that is already on your machine.

    What you get

    A guide that plans your route and shows its sources.

    01Plan your route

    An hour, a day, three days or a week.

    Pick your time, your goal (get the gist, ship a change, own it or rebuild it) and your background. Onramp plans a day-by-day route and draws it as a road, with exits, rest stops, checkpoints and a you are here marker. Your progress is saved.

    One guide serves every route. The planning happens in the page, so changing your mind costs nothing.

    PaperMind · 3-day route · get the gist
    02Every claim checked

    Citations a script can fail.

    Each claim carries a citation: a file, a line range and a piece of text from those lines, like store.py:29–38. verify.py opens every file and checks that the text is really there.

    Drifted line numbers are re-anchored automatically. A claim whose text isn't in the file fails, and gets rewritten from the actual code. When you click a citation, the code you see is copied from your file, never written by the model.

    $ python verify.py . --fix
    FIXED flows[2].steps[3]: api.js:88-97 → api.js:91-100
    ERROR lesson 'care-auth': anchor 'refresh_token(' is not in backend/auth/utils.py
    … Claude re-reads the file and rewrites the claim …
    $ python verify.py . --fix
    OK every citation verified against the code at commit fcb26da
    03The why

    Why it's built this way, from your own history.

    Onramp reads the git history and, if you say yes, your local Claude Code transcripts for the project. For a project you built with Claude, a file card can show the prompt that led to the file and what Claude said when it made the change.

    Every decision in the guide is labelled documented (there is a commit, doc or quote) or inferred (reasoned from the code).

    02

    Scan the repository

    script · no model

    scan.py takes inventory in seconds, without a model. It reads .gitignore, counts files and lines per language, parses manifests, finds entry points and env vars, and builds an import graph for JS/TS, Python, Go, Rust, Java/Kotlin, C/C++, Ruby and PHP. It also reads git history for churn and a timeline.

    Every file then gets an importance score. The score goes up with how many files import it, how often it changed, how big it is and whether execution starts there. Claude reads in that order, so the first hour goes to the files that matter. The maps in the guide are drawn from this graph rather than imagined.

    $ python scan.py .
    ONRAMP SCAN PaperMind
    files 186 (source 153, tests 0), 31575 lines of code
    languages: Python 69%, JavaScript 30%, CSS 1%
    git: 20 commits by 2 author(s), 2025-11-20 -> 2026-10-29
    claude sessions: 1 transcript(s)
     
    read first (importance):
    100.0 frontend/src/components/ui/primitives.jsx used by 30
    89.5 backend/main.py used by 5
    80.9 core/agents/base_agent.py used by 11
    79.1 core/agents/orchestrator.py used by 2
    03

    Ask about history

    you decide

    If the scan finds Claude Code transcripts for the project, Claude asks once whether to use them. If you say yes, sessions.py pairs every file Claude wrote or edited with the prompt that led to it and the explanation Claude gave just before the edit. That becomes evidence for the "how it was built" and "why" chapters.

    Transcripts are read from your disk and never leave it. Anything that looks like an API key or token is redacted. Claude Code deletes transcripts after about 30 days by default, so older projects lean on git history instead.

    Claude
    I found 1 Claude Code session for this project. Should I use it
    to explain why things were built? It stays on your machine.
    04

    Read the code

    Claude

    Claude reads in a fixed order:

    1. the README, CLAUDE.md and docs
    2. manifests and config, which say how it installs and runs
    3. entry points, then the top of the importance ranking
    4. for each important user action, every call from the entry point to storage and back

    One rule overrides speed: Claude never describes a file it has not opened. On large repositories it fans out, one subagent per module, each writing file cards in parallel, while Claude traces the main flows itself.

    05

    Write the guide

    Claude

    The guide is a JSON file of lessons, the stops on your route. Each lesson teaches one idea and records which chapter it belongs to, how essential it is (core, standard or deep), how many minutes it takes and which goals it serves. That metadata is what lets one guide become a 1-hour route or a 1-week route.

    Around the lessons sit the structured parts: traced flows, file cards, the stack with primers for newcomers, the data model, build-order milestones, decisions marked documented or inferred, risks and exercises. Every technical sentence carries a citation.

    {
    "id": "flow-order", "chapter": "flows", "tier": "core", "minutes": 7,
    "summary": "The page posts the checked SKUs, the server prices them,
    the store saves the order and the page shows the total.",
    "body": "... unknown SKUs raise [[app/store.py:29-38|def place_order(]] ..."
    }
    06

    Verify every claim

    script · no model

    verify.py opens every cited file and checks three things: the file exists, the lines exist, and the quoted text is inside those lines. Each citation ends one of three ways:

    • Verified. The text is where the guide says it is.
    • Re-anchored. The text is in the file but the line numbers drifted, so the citation moves to where it really is.
    • Rejected. The text is nowhere in the file. Claude re-reads the code and rewrites the claim, then runs the check again.

    The guide is only built when the check passes. Its badge states how many claims were checked and at which commit.

    $ python verify.py . --fix
    OK 35/35 citations verified across 4 files, 0 auto-fixed
    07

    Render one file

    script · no model

    render.py builds a single HTML page with the guide, the computed maps and the real code behind every citation embedded in it. It opens straight from disk with no server, and works offline apart from fonts, diagrams and syntax colours. It also writes GUIDE.md, the same guide as markdown, for GitHub and for other agents. Render with --public to share it without your local paths.

    $ python render.py . --open
    ONRAMP RENDER .onramp/index.html (134 KB, 12 lessons, 28 code excerpts)
    markdown .onramp/GUIDE.md
    08

    Learn it your way

    you

    The guide opens on three questions: how much time you have, what you want to do, and your background. Then it plans your route and draws it as a road.

    • Stops start with a one-line summary, then the explanation, a "go deeper" section and a checkpoint question.
    • Citations open the real code beside the text, with the cited lines highlighted and links to your editor or GitHub.
    • Files shows every file the guide explains, what it depends on and what uses it.
    • Map shows the architecture, the computed dependency graph, languages and history.
    • Search covers stops, files, ideas and flows. Press Ctrl K.

    Prefer a conversation? /onramp tutor walks the same route in chat, one stop at a time, and remembers where you stopped.

    Questions

    Before you install.

    Does my code leave my machine?

    Onramp runs inside your own Claude Code session, so Claude reads your code the way it does for any task. The scripts make no network calls and the guide is a local file. Claude Code transcripts are only read if you agree. Text that looks like a key or token is redacted.

    Will it change my code?

    No. It only writes inside .onramp/ in your repository: the guide page, a markdown copy and the source JSON.

    What does "checked" actually mean?

    Every citation names a file, a line range and a short piece of text from those lines. verify.py confirms the file exists, the lines exist and the text is in them. That catches invented functions, wrong files and stale line numbers. It cannot judge whether an explanation is wise, so judgements are written as judgements, and decisions say whether they are documented or inferred.

    How big a repository can it handle?

    The scanner takes seconds even on large repositories. Claude reads the most important files first and splits big codebases across subagents, one per module. On a very large monorepo, point it at the package you care about, for example /onramp packages/api.

    Does it work in Cursor, Codex or Gemini CLI?

    It is built and tested for Claude Code. The skills CLI installs it for any agent that reads SKILL.md, and the scripts are plain Python, so it should work wherever an agent can read files and run Python.

    Can I share a guide?

    Yes. Render it with --public to drop your local paths and link code to GitHub, then host the single HTML file anywhere. The demos on this page were published that way.
